# AGENTS: правила работы над проектом

Этот файл предназначен для Codex, Claude Code и других ИИ-разработчиков, которые будут автономно работать над проектом `Живое Городище`.

## 1. Главная цель

Создать интерактивную платформу коллективного строительства исторического поселения.

Не превращать проект в статичный лендинг. Основные сущности должны управляться через БД и админ-панель.

## 2. Приоритеты

1. Рабочая интерактивная карта.
2. Управляемые здания и маркеры.
3. Слоты поддержки.
4. Корректный платежный сценарий.
5. Летопись.
6. Волонтерские заявки.
7. Админ-конструктор.
8. Аналитика.

## 3. Технологические решения

Использовать:

- Next.js App Router;
- TypeScript;
- Tailwind CSS;
- shadcn/ui;
- lucide-react;
- Supabase;
- ЮKassa;
- Telegram Bot API;
- SMTP.

Не добавлять новый крупный фреймворк без веской причины.

## 5. Правила данных

- Деньги хранить в копейках.
- Координаты карты хранить в процентах.
- Донат считать оплаченным только после webhook.
- Webhook должен быть идемпотентным.
- Публичное имя не показывать без согласия.
- Админские действия логировать.

## 6. Правила UI

- Следовать `DESIGN_SYSTEM.md`.
- Главный визуальный источник: `Референс.png`.
- Использовать реальные ассеты из `assets/Здания`.
- Не делать маркетинговую hero-страницу вместо продукта.
- Первый экран должен быть рабочей картой.
- На mobile использовать bottom sheet для карточки здания.
- Не вкладывать карточки в карточки.
- Не использовать декоративные градиентные орбы и абстрактные фоны.

## 7. Публичная карта

Карта должна:

- брать активную версию из БД;
- показывать видимые маркеры;
- позиционировать маркеры в процентах;
- открывать карточку здания;
- работать на 360px;
- быть доступной с клавиатуры.

## 8. Админка

Админка должна быть рабочим инструментом.

Требования:

- защищенные маршруты;
- проверка ролей на сервере;
- таблицы с фильтрами;
- формы с валидацией;
- понятные статусы;
- запись аудита;
- подтверждение опасных действий.

Админка может быть визуально проще публичной части.

## 9. Платежи

Правильный сценарий:

1. Создать donation `pending`.
2. Создать платеж в ЮKassa.
3. Получить webhook.
4. Проверить, что event еще не обработан.
5. Обновить donation на `paid`.
6. Пересчитать суммы.
7. Создать запись летописи.
8. Отправить уведомления.

Неправильно:

- переводить donation в `paid` после возврата пользователя на success page;
- удваивать сумму при повторном webhook;
- хранить платежные секреты на клиенте.

Текущий прототип уже имеет `POST /api/donations`. При пустом Supabase env он возвращает mock-ответ, при заполненном env создает `pending` donation в Supabase. Не переводить реальный Supabase-донат в `paid` без webhook.

## 10. Безопасность

Обязательно:

- RLS в Supabase;
- server-side role checks;
- защита `/admin`;
- проверка входных данных;
- ограничения загрузки файлов;
- аудит критичных изменений;
- env-переменные для секретов.

## 11. Тестирование

Перед завершением задачи проверить:

- desktop;
- mobile 360px;
- выбранное здание на карте;
- страницу здания;
- форму доната;
- форму волонтера;
- пустые состояния;
- ошибки;
- отсутствие наложения текста.

После значимых frontend-изменений запускать dev server и проверять через браузер.

## 12. Документация

При изменении архитектуры обновлять:

- `SPEC.md`;
- `DATA_MODEL.md`;
- `IMPLEMENTATION_PLAN.md`;
- `DESIGN_SYSTEM.md`;
- `AGENTS.md`, если меняются правила работы.

## 13. Codex Subagents

Проектные Codex-субагенты описаны отдельными файлами в:

```txt
.agents/codex-subagents/
```

Это не `.claude/agents` и не новые системные tool-типы. Для Codex эти файлы являются role prompts, которые оркестратор читает перед делегированием задачи встроенному `worker` или `explorer`.

Правила:

- перед кодингом определить этап работы и свериться с `.agents/codex-subagents/task-routing.md`;
- перед вызовом субагента прочитать соответствующий файл ассистента;
- для реализации использовать `worker` с точным ownership файлов;
- для QA, security review и browser verification использовать `explorer` read-only;
- coding-agent обязан учитывать, что он не один в кодовой базе, и не откатывать чужие изменения;
- параллельная работа разрешена только при непересекающихся write scopes.

MCP:

- Context7 использовать для проверки актуальной документации библиотек и фреймворков, когда задача зависит от API Next.js, React, Supabase, Tailwind, shadcn/ui, lucide-react или Playwright;
- Playwright MCP использовать для локальной browser-проверки после значимых frontend/admin UI изменений, включая desktop и mobile 360px;
- в MCP-запросы нельзя отправлять секреты, токены, реальные персональные данные или большие фрагменты приватного кода.

Файлы в `.agents/codex-subagents/` считаются частью проектной документации. Их нужно обновлять вместе с `AGENTS.md`, `SPEC.md`, `DATA_MODEL.md`, `IMPLEMENTATION_PLAN.md` и `DESIGN_SYSTEM.md`, если меняются архитектура, платежный сценарий, роли, RLS, структура админки, порядок разработки или UI-правила.

## 14. Чего не делать в MVP

- Не делать мобильное приложение.
- Не добавлять NFT/крипто-механику.
- Не строить форум.
- Не добавлять AI-функции в продукт без отдельного решения.
- Не усложнять аналитику до полноценной BI-системы.
- Не делать 3D-карту, если 2D-интерактив закрывает задачу.
