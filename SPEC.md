# SPEC: Живое Городище

## 1. Назначение

`Живое Городище` — интерактивная веб-платформа для коллективного строительства исторического славянского поселения X-XIII веков.

Пользователь должен видеть карту поселения, выбирать конкретное здание или объект сбора, делать вклад, попадать в цифровую летопись и следить за прогрессом. Администратор должен управлять картой, зданиями, слотами, изображениями, статусами, летописью, волонтерами и аналитикой без изменения кода.

Проект не является статичным лендингом. Все ключевые публичные сущности должны храниться в базе данных и редактироваться через административную панель.

## 2. Цели MVP

MVP должен позволять:

- открыть интерактивную карту поселения;
- кликнуть на маркер здания и увидеть карточку;
- открыть отдельную страницу здания;
- выбрать слот поддержки;
- пройти тестовый, а затем реальный сценарий пожертвования;
- автоматически обновить прогресс после подтверждения оплаты;
- создать запись в летописи;
- отправить заявку волонтера;
- управлять картой, зданиями, слотами и контентом из админки.

## 3. Основной стек

- Framework: Next.js App Router.
- Language: TypeScript.
- UI: React, Tailwind CSS, shadcn/ui, lucide-react.
- Database: Supabase Postgres.
- Auth: Supabase Auth.
- Storage: Supabase Storage.
- Payments: ЮKassa.
- Notifications: Telegram Bot API.
- Email: SMTP.
- Deploy: Vercel + Supabase.

## 4. Роли

### Гость

Может:

- смотреть карту;
- открывать карточки зданий;
- смотреть страницы зданий;
- смотреть летопись;
- отправлять донат;
- отправлять заявку волонтера.

Не может:

- открывать личный кабинет;
- видеть административные данные;
- редактировать контент.

### Участник

Может:

- смотреть историю своих донатов;
- смотреть свои волонтерские заявки;
- видеть баллы и статус;
- получать сертификаты;
- управлять публичностью своего имени.

### Редактор

Может:

- редактировать здания;
- редактировать изображения;
- редактировать тексты;
- модерировать летопись.

Не может:

- менять платежные настройки;
- менять роли;
- видеть системные ключи.

### Администратор

Может:

- управлять картой;
- управлять маркерами;
- управлять зданиями;
- управлять слотами сборов;
- видеть донаты;
- экспортировать данные;
- управлять волонтерами;
- смотреть аналитику.

### Суперадмин

Может:

- управлять ролями;
- управлять интеграциями;
- управлять системными настройками;
- смотреть аудит.

## 5. Публичные страницы

### `/`

Главная интерактивная карта поселения.

Обязательные элементы:

- верхняя навигация;
- карта поселения;
- кликабельные маркеры;
- фильтр по зонам;
- фильтр по статусам;
- карточка выбранного здания;
- блок общей статистики;
- последние вклады;
- список объектов поселения.

Desktop:

- карта занимает основную область;
- карточка выбранного здания открывается поверх карты слева или справа;
- статистика может быть вынесена в правую колонку.

Mobile:

- карта остается главным экраном;
- карточка выбранного здания открывается как нижняя панель;
- маркеры должны оставаться кликабельными;
- навигация сворачивается.

### `/objects/[slug]`

SEO-страница здания.

Обязательные элементы:

- название;
- зона;
- статус;
- главное изображение;
- галерея;
- описание;
- историческая справка;
- общий бюджет;
- собранная сумма;
- процент прогресса;
- список слотов поддержки;
- список публичных вкладчиков;
- фрагмент летописи по зданию.

### `/donate/[itemId]`

Страница или модальное состояние выбора вклада.

Поля формы:

- имя;
- email;
- телефон, опционально;
- сумма;
- согласие на обработку персональных данных;
- согласие на публикацию имени;

### `/payment/success`

Страница успешного возврата после платежа.

Важно: успешный возврат пользователя не должен засчитывать донат как оплаченный. Финальное подтверждение происходит только через webhook ЮKassa.

### `/chronicle`

Записи:

### `/volunteers`

Страница для волонтеров.

Обязательные элементы:

- описание участия;
- форма заявки;
- выбор объекта;
- предпочтительные даты;
- навыки;
- контактные данные;
- согласия.

### `/account`

Личный кабинет участника.

Разделы:

- профиль;

## 7. Статусы

### Статусы здания

- `idea` — Замысел.
- `fundraising` — Сбор открыт.
- `building` — Строится.
- `finishing` — Завершение.
- `active` — Действует.
- `archived` — Архив.

### Статусы слота

- `available` — доступен.
- `reserved` — зарезервирован.
- `funded` — закрыт.
- `hidden` — скрыт.

### Статусы доната

- `pending` — создан.
- `paid` — оплачен.
- `cancelled` — отменен.
- `failed` — ошибка.
- `refunded` — возвращен.

### Статусы заявки волонтера

- `new` — новая.
- `reviewing` — в обработке.
- `approved` — подтверждена.
- `declined` — отклонена.
- `completed` — отработана.

## 8. Платежный сценарий

1. Пользователь выбирает слот поддержки.
2. Заполняет форму.
3. Система создает запись `donations` со статусом `pending`.
4. Система создает платеж в ЮKassa.
5. Пользователь переходит на страницу оплаты.
6. ЮKassa отправляет webhook.
7. Сервер проверяет событие и идемпотентность.
8. Донат переводится в `paid`.
9. Обновляется прогресс слота и здания.
10. Создается запись летописи.
11. Отправляется email.
12. Отправляется Telegram-уведомление администратору.

Нельзя засчитывать донат только по redirect на `/payment/success`.

## 9. Интерактивная карта

Карта хранится как `map_versions`.

Маркеры хранятся отдельно в `map_markers`.

Координаты:

- `x_percent`: число от 0 до 100;
- `y_percent`: число от 0 до 100.

Это требуется, чтобы маркеры сохраняли позицию при адаптивном масштабировании карты.

Публичная карта должна:

- загружать активную карту;
- загружать видимые маркеры;
- открывать карточку здания по клику;
- поддерживать клавиатурную навигацию;
- не ломаться на экранах от 360px.

## 10. Нефункциональные требования

- Адаптивность: от 360px.
- SEO: отдельные страницы зданий.
- Производительность: оптимизированные изображения, lazy loading.
- Доступность: alt, aria-label, фокус, управление клавиатурой.
- Безопасность: RLS, роли, server-side checks.
- Надежность платежей: webhook idempotency.
- Масштабируемость: минимум 100 зданий, 1000 слотов, 100000 записей летописи.

## 11. Критерии готовности MVP

MVP готов, если:

- администратор может загрузить карту и сделать ее активной;
- администратор может создать здание;
- администратор может поставить маркер здания на карту;
- пользователь может открыть карточку здания с карты;
- пользователь может открыть страницу здания;
- пользователь может выбрать слот поддержки;
- платеж проходит через ЮKassa;
- прогресс обновляется после webhook;
- запись появляется в летописи;
- волонтер может отправить заявку;
- администратор может обработать заявку;
- критичные действия пишутся в аудит;
- сайт корректно работает на desktop и mobile.
